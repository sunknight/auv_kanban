# Kanban 看板操作 Skill

本 Skill 通过 `kanban` CLI 操作当前项目的 `.kanban/` 看板。看板数据完全基于 Markdown 文件与目录。

## 目录约定

- 看板数据目录：项目根的 `.kanban/`
- **任务实体**：`.kanban/tasks/<ID>-<名称>/`，ID 为 4 位数字（如 0007），永不复用。**实体目录创建后冻结——永不移动、永不改名**（即使修改标题）。所有任务素材（main.md、设计文档等）都放这里。
- **栏归属（进度）**：只在 `.kanban/board.yml` 的 `order` 字段记录（order 里包含某 ID 的栏即该任务的栏）。栏有四种：`backlog`（待办）、`ready`（允许执行）、`doing`（进行中）、`done`（完成）。
- **栏目录（只读软链视图）**：`.kanban/<栏>/` 下放指向 `../tasks/<ID>-<名>` 的软链，仅为方便人用 Finder/编辑器浏览。**勿手工增删栏软链或实体**——改进度用 `kanban move`，软链由系统自动同步；软链出错用 `kanban sync` 重建。
- **标题与目录名解耦**：显示名来自 `main.md` 的 H1（`# 标题`），目录名是创建时冻结的初始名。改标题只重写 H1，目录不变。
- 主文件：`<任务实体目录>/main.md`，固定四段：`# 标题`、`## 描述`（原始需求，**创建后永不改写**——首次填充除外，见「[一条指令建任务并执行（/kanban create）](#一条指令建任务并执行kanban-create)」）、`## 提示词`、`## 子任务`。
- **子任务格式**（`## 子任务` 段内每行）：`- [ ] NN [标签] 文本`。
  - `NN` = 2 位唯一编号（01/02/03…），用于跨命令定位（`kanban check <ID> NN`）。新子任务编号 = 现有最大编号 +1。
  - `[标签]` 可选，如 `[补充]`（由 `kanban update` 追加的需求带此标签）。无标签则省略。
  - 示例：`- [x] 01 设计表单`（普通拆解）、`- [ ] 03 [补充] 存档要二次确认`（补充需求）。
  - 旧格式无编号子任务兼容（`- [ ] 文本`），`check` 时位置序号兜底。
- **延后事项（todo.md，可选）**：任务子目录下的 `todo.md` 记录**本次不做、但要留待后续处理**的事项（边界外需求、技术债、后续优化）。与子任务的区分：**子任务 = 本任务必须完成、全勾完才 done；todo = 明确延后、不阻塞任务完成**。
  - 格式与子任务一致：`- [ ] NN 文本`（`NN` 2 位编号，追加时 = 现有最大编号 +1；**增量追加，不重写**已有行）。文件不存在则新建（建议首行 `# 延后事项` + 空行）。
  - 标记完成：`kanban todo-check <ID> NN` / 取消 `kanban todo-uncheck <ID> NN`（幂等）；Web 详情的 todo.md 预览里点 checkbox 也可以。
  - 添加事项：Web 详情的 todo.md 预览里点「＋添加」填标题与内容（内容多行写在标题下方，形似 `- [ ]` 的行会被自动转义）；只 append 到文件末尾，编号自动递增。任务尚无 todo.md 时，详情文档区会显示虚线的「＋ todo.md」占位标签，点它同样弹出表单——**提交成功才创建文件**，取消不产生文件。
  - 有未完成 todo 时 Web 卡片显示 `todo N` 标签——**done 栏任务同样显示**（提醒还有遗留）；全部勾完后标签消失（文件保留作历史）。
  - todo 不进 `## 子任务`、不进 `kanban progress`（进度只算子任务）、不阻塞 move done。
- **任务文档**：实体目录下除 `main.md` 外的文档，在 Web 详情里按固定语义顺序展示：`main.md` → `todo.md`（延后事项）→ `logs.md`（执行进展日志）→ `design.md` → `plan.md` → `readme.md` → `notes.md` → 其余按文件名字母序。
- **任务文档预览（Web 详情）**：任务目录内（含任意深度子目录）的白名单文件均可在线预览——文本类 txt/md/markdown/sql/json/xml/yml/yaml/log/html(源码)、csv（渲染表格）、图片 png/jpg/jpeg/gif/webp/svg/bmp/avif、docx（转 HTML）、xlsx/xls（转表格，多 sheet 切换）。子目录文件经「🗂 文件」浮层文件树点选预览。路径穿越与软链外指一律被服务端拒绝。
- **目录清单（`files.md`，按需自动生成）**：任务目录里出现**不可预览文件**（上述白名单之外，如 zip/exe/bin）或**子目录**后，Web 打开任务详情时会自动生成/更新 `files.md`——tree 风格**递归**列出目录全部文件（含子目录内文件，按缩进展开；**软链一律只列名不展开**，无论指向任务内外——既防止清单被软链引到任务外，也杜绝软链环死循环）；tree 块整体包在 ``` 代码围栏内（markdown 渲染逐行显示、换行不丢）；详情「任务文档」标题行最右侧的「🗂 文件」按钮即其入口——点开浮层文件树（与 `files.md` 同序、全量列文件），点选任意文件在预览区打开且浮层不关闭，不可预览文件灰显；该按钮不占固定文档行；固定文档不写作用说明。**其他文件的作用说明由智能体写入**：往任务目录写入任何不可预览文件后，在 `files.md` 中给该文件行末尾补「 ` —— 一句话说明` 」（该文件尚无对应行或尚无 `files.md` 时，按现有 tree 格式手工补建/补行，行写在围栏内、缩进与同级对齐）；服务端之后刷新清单结构时，会**按相对路径保留**这些说明（子目录内文件直接在其行上补说明即可；不同子目录里的同名文件靠相对路径区分，不会串）。

## 命令清单

```
kanban show <ID>              # 显示任务详情（含当前绝对路径、栏、名称、描述、提示词、子任务带编号/标签）
kanban list [--column <栏>]   # 列出任务
kanban new <名称>             # 在 backlog 创建新任务
kanban update <ID> <需求>        # 对任务追加一条补充需求（写入 ## 子任务，带 [补充] 标签）并重开到 doing，默认追加后立即执行（补了就做）
kanban update --no-run <ID> <需求> # 同上，但只补需求、不立即执行（稍后手动 /kanban run）
kanban move <ID> <栏>         # 移动任务到指定栏（只改 board.yml，实体不动）
kanban check <ID> <编号>      # 勾选指定编号子任务（设为已完成，非 toggle，幂等）
kanban uncheck <ID> <编号>    # 取消勾选指定编号子任务（设为未完成，非 toggle，幂等）
kanban todo-check <ID> <编号>    # 勾选指定编号 todo 延后事项（todo.md，幂等）
kanban todo-uncheck <ID> <编号>  # 取消勾选指定编号 todo 延后事项（幂等）
kanban progress <ID>          # 显示进度
kanban init [项目]            # 初始化看板
kanban sync                   # 重建所有栏软链以对齐 board.yml（修复断链/孤儿，幂等）
```

> **关于 `run` 与 `--design`**：`run` 不是 `kanban` CLI 子命令，而是 skill 层的执行流程（见下方「任务执行流程」），由 agent 解释执行一连串上面的 CLI。`--design` 是 `run` 的 skill 层参数（`/kanban run --design <ID>`），非 CLI flag——作用是只做设计/预研，产出 `design.md`/`plan.md` 后任务回 `ready` 待实施，下次 `/kanban run <ID>` 读已有设计直接进入实施。

`/kanban` 的全部入口、命令形态与向导分步，一图总览（⇒ 表示「把向导收集到的参数拼成等价斜杠命令」；所有分支最终都落到上方「命令清单」的 CLI 原语执行）：

│   ├─ run                      取 ready 队首一个 → 全流程 → 完成后问「继续下一个？」

    │
    ├─ Q1 做什么？（直入分支时跳过）
    │   ├─ 执行任务 run      （ready 有任务 → 推荐）
    │   ├─ 新建任务 create   （ready 空 → 推荐）
    │   ├─ 补充需求 update
    │   ├─ 查看/速查
    │   └─ Other：低频操作直接说（move/check/uncheck/progress/sync/init/archive/delete）
    │
    ├─ run 分支 —— 两题合并一次问
    │   ├─ 任务？  ready 队首（推荐）｜ready 第 2/3 个｜Other 输 ID
    │   │          （ready 空 → 改为新建｜返回重选，不列 backlog）
    │   ├─ 模式？  全流程→done（推荐）｜只预研 --design→回 ready 停
    │   └─ ⇒ /kanban run [--design] <ID>
    │
    ├─ create 分支 —— 三题合并一次问
    │   ├─ 方式？  新建并执行（推荐）｜只设计 --design｜补录 --backfill
    │   ├─ 标题？  agent 候选（推荐）｜候选 2｜草稿名后改（H1 可改·目录名冻结）｜Other 输入

    │   │          （backfill：描述自动从会话提炼，此题忽略）
    │   └─ ⇒ /kanban create [--design|--backfill] <标题>（+描述行）
    │

    │   ├─ 需求？    Other 输入文本｜先看子任务清单再答｜取消

```

## 裸 /kanban 交互向导（无参数时分步询问）

用户输入 `/kanban ?`、裸 `/kanban`（后面不带任何命令、参数、自然语言意图），或 `/kanban <分支> ?`（如 `/kanban run ?`）时，**不猜、不默认执行任何任务**，改用 `AskUserQuestion` 工具分步询问，收集齐参数后拼出等价斜杠命令进入对应流程。

**向导进入方式（`?` 即「帮我问」）**：

| 输入 | 行为 |
|------|------|
| `/kanban`（裸）或 `/kanban ?` | 从第一问「做什么？」开始的完整向导 |
| `/kanban run ?` | 跳过第一问，直接进 run 分支（两题合并一次问） |
| `/kanban create ?` | 直接进 create 分支（三题合并一次问） |
| `/kanban update ?` | 直接进 update 分支（三题合并一次问） |

**豁免**：输入已含命令与实参（`/kanban run 0007`、`/kanban create 修登录`…）或自然语言意图明确（「执行 0007」「建个任务修复登录」）时直接走对应流程，**不进向导**；唯一例外是命令后只跟 `?`——那是显式要求进向导（查看/速查分支无 `?` 直入形态，经第一问进入）。

### 向导总原则（硬性）

1. **全程 `AskUserQuestion` 点击式询问**——禁止纯文本发问；自由文本参数（标题、需求内容、ID）引导用户点 **Other** 输入，一句话即可。每问显式选项 **2-4 个**——Other 由工具自动追加、不计入，不能只给 1 个显式选项。
2. **合并提问省往返**：`AskUserQuestion` 一次调用最多可带 4 个问题，相互独立的参数**合并进同一次询问**（run 分支两题一问、create/update 分支三题一问），用户一次点选完即开跑；只有「下一步问什么」依赖于上一问答案时才分轮。
3. **选项动态生成**：开场先执行 `kanban list` 取全栏真实任务（ID+名称+栏），所有任务候选来自这份输出，**绝不凭空编造**；推荐项按现状调整——ready 有任务时首推「执行任务」，ready 空时首推「新建任务」。
4. **推荐项置首**，标注「（推荐）」。
5. **问完即执行，不追加确认**：每个参数都是用户亲自点选的，收集齐后直接进入对应流程（run 三阶段 / create / update），不再多问一轮「确认吗」。
6. **Other 即逃生口**：向导未覆盖的低频操作（move / check / uncheck / progress / sync / init / archive / delete），用户在任一问选 Other 直接说（如「把 0007 挪回 backlog」），按「命令清单」执行对应 CLI，向导不逐项枚举。
7. **看板未初始化**：`.kanban/` 不存在时，第一问改为「看板未初始化，现在 `kanban init` 吗？」——「初始化（推荐）」/「取消」。

### 第一问：现在要做什么？（单问；`/kanban <分支> ?` 直入时跳过本问）

| 选项 | 进入分支 |
|------|---------|
| 执行任务（run）——ready 有任务时推荐 | run 分支 |
| 新建任务（create）——ready 空时推荐 | create 分支 |
| 给已有任务补需求（update） | update 分支 |
| 查看与速查（看板 / 常用命令） | 查看/速查分支 |

选项的 description 里带一句看板现状摘要（如「ready 2 个，队首 0012 修复分页」），帮用户不看板也能选对。

### run 分支（两题合并一次问）

| 问题 | 选项 |
|------|------|
| ① 执行哪个任务？ | ready 队首 `<ID> <名称>`（推荐）；ready 第 2、3 个（若有）；Other 输入任意 4 位 ID |
| ② 执行模式？ | 全流程：设计+实施 → done（推荐）；只做预研设计（--design）→ 回 ready 停 |

- ready 为空时**不列 backlog 候选**——run 只认 ready 栏，与直接命令的硬性约束一致：①的选项退化为「改为新建任务（转 create 分支，推荐）」/「返回重选（回第一问）」/ Other 输 ID。
- 收集完拼 `/kanban run [--design] <ID>`，进入「任务执行流程」。

### create 分支（三题合并一次问）

| 问题 | 选项 |
|------|------|
| ① 怎么建？ | 新建并立即执行（推荐）；新建只做设计（--design）；补录本会话已在做的工作（--backfill） |
| ② 标题？ | agent 起草候选（推荐，从会话上下文/看板现状提炼）；第二个候选（若有）；先用草稿名，澄清后再改（H1 可改、目录名冻结）；Other 直接输入 |
| ③ 附原始描述吗？ | 跳过（推荐，细节留到设计澄清环节逐点问）；由 agent 从上下文提炼一句作背景；Other 输入原始需求 |

- `## 描述` 段创建后冻结，③是留下用户原话的唯一入口——用户有明确需求时应引导 Other 输入；无话可说点「跳过」即可。
- ①选了 `--backfill`：②的候选从本会话已完成工作提炼；③自动忽略（描述从会话历史提炼）。
- 收集完拼 `/kanban create [--design|--backfill] <标题>`（③有输入则作为标题后的描述行），进入「一条指令建任务并执行」。

### update 分支（三题合并一次问）

| 问题 | 选项 |
|------|------|
| ① 给哪个任务补？ | doing 栏最前 1-3 个 `<ID> <名称>`（有则推荐第一个）；最近 done 的 1 个；Other 输入任意 ID |
| ② 补完后？ | 立即执行刚补的这条（推荐，默认行为）；只补需求不执行（--no-run） |
| ③ 补充什么需求？ | Other 输入需求文本；先看该任务子任务清单再答（`kanban show` 展示后重问③）；取消补充 |

- 收集完执行 `kanban update [--no-run] <ID> <需求>`，随后按「对已有任务补需求并重开」处理（默认立即执行）。

### 查看/速查分支（只读，一问；看详情再补一问）

| 问题 | 选项 |
|------|------|
| 看什么？ | 常用命令速查（推荐，输出可复制的命令速查表）；整板概览（各栏任务一览）；某任务详情（追问看哪个：候选列表 / Other 输 ID → `kanban show`）；进行中任务的进度（doing 各任务 `kanban progress`） |

**常用命令速查**：用纯文本代码块直接输出下方速查表，**顶部加一行当前看板现状**（来自开场 `kanban list`，如「ready 2 个，队首 0012 修复分页；doing 1 个」）。输出即停、不追问——用户复制某条命令直接输入，按「豁免」规则带命令执行，不回向导。

```text
# 常用命令速查（复制即用，<ID> 换成 4 位任务号）
/kanban run                       # 取 ready 队首执行（全流程 → done）
/kanban run <ID>                  # 执行指定任务（全流程）
/kanban run --design <ID>         # 只预研设计 → 回 ready 停，不实施
/kanban create <标题>             # 一句话建任务并立即执行（首行=标题，后续行=描述）
/kanban create --design <标题>    # 建任务只做设计
/kanban create --backfill <标题>  # 补录本会话已在做的工作（落 doing）
/kanban update <ID> <需求>        # 补需求并重开，默认立即执行
/kanban update --no-run <ID> <需求>  # 只补需求，稍后手动 run
# 参数记不清？命令后加 ? 进分步向导：/kanban ? 全向导；run/create/update ? 直入分支
# 查看类（也可直接说「看看板」「0007 进度」）：
kanban list [--column ready|doing|backlog|done]    # 列任务
kanban show <ID> / kanban progress <ID>            # 详情 / 进度
```

其余查看为只读操作，结果用纯文本/表格呈现即结束，不追问后续。

## 任务执行流程（/kanban run，支持 `--design` 预研）

`/kanban run` 由 agent 解释执行，**不是 `kanban` CLI 子命令**。它支持一个 skill 层参数 `--design`（预研模式）：只做到「设计+计划文档生成、疑问澄清完毕」即停，任务回 `ready` 待实施，下次再 `/kanban run` 直接读已有设计进入实施。

`/kanban run` 有三种输入形态：

| 形态 | 含义 | 流程终止点 |
|------|------|-----------|
| `/kanban run <ID>` | 执行指定任务（含设计+实施） | 实施完成（move done） |
| `/kanban run`（不带 ID） | 取 ready 队首执行（含设计+实施） | 实施完成（move done） |
| `/kanban run --design <ID>` | **只做预研/设计**，不实施 | 设计完成（回 ready，停） |

`--design` 的自然语言同义词（与 `update` 同一套意图映射规则）：用户说「预研/做设计/做方案/先设计 <ID>」「<ID> 先别动手，只出方案」「<ID> 调研一下怎么做」等表达「只要设计、暂不实施」之意时，一律按 `/kanban run --design <ID>` 处理。

### 步骤 0：确定目标任务（区分有无 ID / 是否预研）

| 输入形态 | 如何确定目标任务 |
|---------|----------------|
| `/kanban run <ID>` 或 `/kanban run --design <ID>`（带 4 位 ID） | 直接用该 ID（如 `0007`）。ID 不存在时告知用户并停。 |
| `/kanban run`（不带 ID，无 `--design`） | 执行 `kanban list --column ready`：**只取输出排在最前面的那一个任务**（即 ready 栏的队首，对应 board.yml `order.ready` 数组第一个），拿它的 ID 作为本轮 `<ID>`。**硬性约束：每次最多只取一个；只看 ready 栏；ready 为空（输出「(无任务)」）时直接告知用户「ready 栏无任务」，绝不回退到 backlog/doing/done 等其他栏找任务。** |

> 「排在最前面」的判定依据：`kanban list --column <栏>` 的输出顺序 = board.yml `order.<栏>` 数组顺序（靠前的优先级高），第一行即为该栏队首。

> 注：`--design` 形态**必须带 ID**——预研是用户主动指定的行为，不从队首隐式取任务。

### 三阶段流程（确定 ID 后，带 ID / 不带 ID / `--design` 都走这套）

确定 ID 后，执行分为三个阶段。**`--design` 与普通 run 的唯一行为差异**：`--design` 在阶段 A 末尾即停（回 ready）；普通 run 穿过阶段 A 直接进入阶段 B。

---

#### 阶段 A：设计（预研）

**进入**：确定 ID 后无条件进入（即使已有 `design.md`，也需复核/补充；见下方「设计充分性判断」）。

1. **定位并读取**：执行 `kanban show <ID>`，获取任务绝对路径、描述、提示词、子任务清单。**同时读取任务目录下已有的 `design.md`/`plan.md`（若存在）作为基线**——这是「预研后复用、再 run 直接实施」的关键。
2. **流转到 doing**：执行 `kanban move <ID> doing`（若已在 doing 则跳过）。记下起始时间（用于 logs.md 耗时统计）。
3. **写 logs.md 首条**：在任务子目录创建/追加 `logs.md`，写入第一条——标注本轮**阶段：设计**、起始时间、子任务进度 0/N。详见下方「执行进展记录纪律」。
4. **充分澄清（核心环节，不可跳过）**：对任务中一切歧义、边界、验收标准、技术选型，逐个用 **`AskUserQuestion` 工具**发起**点击式**询问（不要纯文本发问、不要让用户打字长答案）。每问清一个点，把结论**暂记**（内存中累积，作为步骤 5 的「设计决策/澄清结论」素材）。循环直到无悬而未决的问题——**有未决疑问时绝不进入步骤 5 生成文档**。
5. **生成设计文档（前置保存，区别于旧流程）**：
   - 写 `design.md`：背景/问题、目标与验收、设计决策（**含上一步全部澄清结论**）、数据模型或接口、边界与取舍。
   - 写 `plan.md`：带编号的实施清单、依赖与顺序、风险点。
   - **此时即落盘保存**，不要拖到收尾——`--design` 模式随后会停、普通 run 随后会进实施，两都需要设计文档已就绪。
6. **阶段 A 收尾（分流）**：
   - **`--design` 模式（预研）**：往 `logs.md` 追加一条（设计阶段完成、已存档 design+plan、回 ready 待实施）→ 执行 `kanban move <ID> ready` → **用纯文本告知用户**「设计已就绪，存于 `<任务路径>/design.md` 与 `plan.md`；待实施时执行 `/kanban run <ID>`」→ **停，不进入阶段 B**。
   - **普通 run（无 `--design`）**：往 `logs.md` 追加一条（设计阶段完成，继续实施）→ **直接进入阶段 B，不停**。

---

#### 阶段 B：实施

**进入前置：设计充分性判断（硬约束）**。即使是从阶段 A 刚走过来，也要先读最新的 `design.md`（必要时 `plan.md`）核对：
- 若设计**不足以直接开工**（信息缺口、未决问题、验收模糊、关键接口未定）→ **不要硬写代码**，退回阶段 A 步骤 4「充分澄清」补全后再实施。
- 若本次是 `/kanban run <ID>`（**非 `--design`**）且发现任务目录已有完整的 `design.md`/`plan.md`（之前预研留下），**直接读它们作为实施依据进入步骤 1**，不重复做设计——这就是「预研后再 run 直接实施」的落点。

**实施步骤**：

1. **按子任务逐条执行（核心：避免重复执行）**：读取 `## 子任务` 段，找**第一个 `done=false`（未勾选）的子任务**——那就是本轮目标。已完成（`[x]`）的子任务**视为已执行，跳过**，绝不重做。
   - **若该子任务带 `[补充]` 标签**（由 `kanban update` 追加的补充需求）：执行方式 = **增量**——先读已有的 `design.md`/`notes.md`/源码作为基线，只实现这条新需求，**不重写**已完成的工作；文档更新用追加"第 N 轮（YYYY-MM-DD）"小节，不覆盖历史段。
   - **若是普通子任务**（无标签，首次拆解）：按阶段 A 的 `design.md`/`plan.md` 作为依据从头实现。
   - **延后事项入 todo.md，不入子任务**：执行中出现「本次不实现、但要留档后续处理」的事项（边界外的需求、技术债、后续优化），追加到任务子目录 `todo.md`：`- [ ] NN 文本`（编号 = 现有最大 +1；文件不存在则新建）。它们不阻塞任务完成；用户后续处理完可 `kanban todo-check <ID> NN` 勾掉。
   - **无未勾选子任务时**：任务已全部完成，无需再执行，直接进入阶段 C（收尾）。
   - **每个阶段性事件**（完成子任务、关键决策、遇到阻碍、记入 todo 的延后事项）都增量追加一条到 `logs.md`。
2. **勾选完成的子任务**：每完成一个子任务，执行 `kanban check <ID> <编号>`（用子任务的 2 位编号，如 `kanban check 0010 03`）勾上，并往 `logs.md` 追加一条进度。
3. **全部子任务勾选完毕后**：进入阶段 C（收尾）。

---

#### 阶段 C：收尾

1. **归档剩余文档（必须环节，不可跳过）**：`design.md`/`plan.md` 已在阶段 A 生成，此处**仅自检它们非空**（缺则补齐）；`notes.md`/`readme.md` 此时生成。详见下方「任务文档归档纪律」。
2. **写 logs.md 收尾条**：归档完成后、流转 done 前，往 `logs.md` 追加最后一条（全部完成、总耗时、最终状态）。
3. **完成流转**：确认四份文档齐全且子任务全部完成后，执行 `kanban move <ID> done`。

---

### 步骤末：完成后是否继续下一个（仅无 ID 形态）

本轮任务**彻底执行完**（已 `move <ID> done`）后，若本次是**无 ID 的 `/kanban run`** 触发的，执行 `kanban list --column ready` 检查 ready 栏是否还有任务：
- **有任务**：用 **`AskUserQuestion` 工具**发起**点击式**询问（不要用纯文本发问、也不要让用户打字）。把下一个 ready 队首任务的 ID 与名称写进问题里，提供两个可点击选项，例如：「继续执行 `<新队首ID> <名称>`」（推荐，置首）/「到此结束」。用户点选「继续」才取该任务 ID 进入下一轮 run 流程；点选「结束」或选「Other」明确拒绝则停，**绝不擅自执行**。若用户跳过询问未作选择，按「停」处理。
- **无任务**：用纯文本告知用户「ready 栏已无其他任务」，结束（无需询问）。
- **`--design` 形态与带 ID 形态均不适用本步骤**：`--design` 在阶段 A 已停（未到 done）；带 ID 完成即结束，不追问是否继续。

### 执行中的写入纪律（关键，硬性约束）

- **禁止凭记忆或缓存写任何文件**。每次需要读写任务目录前，必须先执行 `kanban show <ID>` 重新定位。任务**实体目录路径稳定**（`.kanban/tasks/<ID>-<名>/`，永不漂移），但任务的**栏归属、子任务勾选、main.md 内容**可能被另一方（人或 Web UI）改写；写前 `show` 重定位 + 读最新内容，是为了避免覆盖他方改动，而非防路径漂移。
- **写入采用"读最新内容 → 行级修改 → 写回"**，避免覆盖他方（人或另一智能体）的最新改动。
- **写入不可预览文件要登记 `files.md`**：往任务目录写入白名单外文件（非 txt/md/sql/csv/json/xml/yaml/log/html/图片/docx/xlsx，如 `.zip`/`.bin`）后，必须在 `files.md` 给该文件行补「 —— 作用说明」（见「目录约定」的 files.md 条目）——Web 无法预览这些文件，清单里的说明是使用者在详情页了解它们的唯一线索。

### 执行进展记录纪律（logs.md，增量日志）

任务执行过程中，在任务子目录维护一份 **`logs.md`**——它是给人/自己在 Web 详情里**准实时查看执行进展**的时间线日志。区别于 `notes.md`（事后总结）：logs.md 是**过程流**，notes.md 是**结论**。

**何时写（每次都是增量追加一条，永不重写已有内容）：**

1. **开始执行**（move doing 之后）：写第一条——开始执行、起始时间、子任务进度 0/N。
2. **每个阶段性事件**：完成一个子任务、做出关键决策、遇到阻碍、完成一个阶段——都追加一条。
3. **结束执行**（归档文档后、move done 前）：写收尾条——全部完成、总耗时、最终状态。

**格式约定（每条一个带时间戳的小节，最新追加在文件末尾）：**

```markdown
## 2026-07-26 14:30:12 — 开始执行

- 已流转到 doing
- 子任务进度：0/3
- 起始时间：14:30

## 2026-07-26 14:42:05 — 完成分析

- 勾选子任务 1「分析」→ 进度 1/3
- 累计耗时：约 12 分钟
- 阶段事件：定位到首屏瓶颈在图片体积

## 2026-07-26 15:10:00 — 任务完成

- 子任务 3/3 全部完成
- 总耗时：约 40 分钟
- 已归档 design/plan/notes/readme
```

**硬性约束：**

- **必须增量追加，不可整体重写**——人在 Web 详情里可能正在看，整体覆盖会丢失此前记录。采用「读最新 → 末尾追加新条目 → 写回」。
- **时间用本地时间，精确到秒**（`YYYY-MM-DD HH:MM:SS`），便于按序读。
- **只记录对进展有意义的事件**，不要逐条工具调用都写；颗粒度=一个可对外汇报的进度点。
- **logs.md 不替代归档文档**：design/plan/notes/readme 仍必须各自沉淀。logs.md 是"过程档案"，四件套是"结论档案"。



### 任务文档归档纪律（必须环节，不可跳过）

每个任务在流转到 `done` 前，**必须**在任务子目录内沉淀以下文档（文件名约定，内容务必覆盖）。注意生成时机随 run 三阶段不同：

| 文件 | 内容 | 生成时机 | 是否必须 |
|------|------|----------|----------|
| `design.md` | 设计方案：背景/问题、目标与验收、设计决策、数据模型或接口、边界与取舍 | **阶段 A（设计）即生成保存**，阶段 C 仅自检非空 | ✅ 必须 |
| `plan.md` | 实施计划：拆分的任务清单（带勾选）、依赖与顺序、风险点 | **阶段 A（设计）即生成保存**，阶段 C 仅自检非空 | ✅ 必须 |
| `notes.md` | 实施记录与总结：改动清单（逐文件）、设计要点回顾、验证结果（测试/手工）、经验反思 | 阶段 C（收尾） | ✅ 必须 |
| `readme.md` | 使用说明：面向使用者的"怎么用"、规则、示例、实现位置指引 | 阶段 C（收尾） | ✅ 必须 |

硬性约束：

- **严禁把任务文档写到项目 `docs/` 或其他全局位置**——一律落在 `kanban show <ID>` 返回的任务子目录里。任务文档随任务实体走，才能被看板完整追溯。
- **写文档前先 `kanban show <ID>` 重新定位**，拿到最新任务目录（同执行中写入纪律）。
- **`move <ID> done` 前自检**：确认上述四份文档都已存在且内容非空；缺则补齐再流转。
- **设计文档前置保存（关键）**：`design.md`/`plan.md` 在**阶段 A 即落盘**，不是收尾才写——这样 `--design` 模式停在 ready 时设计已可被复用，普通 run 进入实施时也有据可依。
- **纯预研任务（`--design` 且尚未实施）停在 ready**：此时 `notes.md`/`readme.md` 尚未生成**属正常**，待后续实施轮（`/kanban run <ID>`）走完阶段 B/C 后补齐。切勿因缺这两份就阻止预研任务回 ready。
- **todo.md（延后事项）不属于归档四件套**：无 todo.md 属正常；有未完成 todo 也**允许 move done**——卡片会持续显示 todo 标签提醒遗留，这正是 todo 的语义（留待后续处理）。事后处理完用 `kanban todo-check <ID> NN` 勾掉，全勾完标签消失。
- 纯调研/无代码改动的任务，`design.md`/`plan.md` 可合并为一份结论文档，但 `notes.md`（结论与发现）+ `readme.md`（如何复用该结论）仍必须。

## 一条指令建任务并执行（/kanban create）

一句话创建带描述的任务并立即执行，省去 `kanban new` + 手填描述 + 单独 `/kanban run` 三步。**底层全用现有能力拼接**：`kanban new` 建任务（CLI 不收描述）→ 用 Edit 工具对 `main.md` 的 `## 描述` 段做**首次填充** → 进入 run 流程或直接归档。不改 CLI。

### 指令形态

| 形态 | 含义 | 流程终止点 |
|------|------|-----------|
| `/kanban create <标题>` | 建任务+填描述+**全流程执行** | 实施完成（move done） |
| `/kanban create --design <标题>` | 建任务+填描述+**只设计**（预研） | 设计完成（回 ready，停） |
| `/kanban create --backfill <标题>` | **把本会话已在做的工作补录为任务**，会话继续在此任务下推进 | 落 **doing**（非 done），等剩余工作完成再收尾 |

### 解析规则（三个变体统一，硬性）

- **第 1 行**：`/kanban create`（含可选 `--design`/`--backfill`）之后的文本 = **标题**。要求简洁、单行、避免 `/` 等目录非法字符（它既是目录名也是 `main.md` 的 H1）。
- **第 1 行之后的全部非空行** = **描述**，原样（含换行）填入 `main.md` 的 `## 描述` 段。
- 仅给标题、无后续行：合法，`## 描述` 段留空，照常走后续流程。

### 变体 1 & 2：`create <标题>` / `create --design <标题>`（全新任务，建+执行）

1. `kanban new "<标题>"` → 从输出解析新 ID（如 `0016`）与任务目录绝对路径。
2. 读 `main.md`，用 **Edit 工具**对 `## 描述` 段做**首次填充**（行级精确替换空描述段为多行描述）。注：此首次填充属创建行为本身，不违反「描述段创建后永不改写」约束。
3. 进入 `/kanban run <新ID>` 流程，**从阶段 A 步骤 2 起完全复用 run 的三阶段**：
   - **普通形态**：阶段 A 设计（澄清→`design.md`/`plan.md`）→ 阶段 B 实施（逐子任务 `check`）→ 阶段 C 收尾（`notes.md`/`readme.md`）→ `kanban move <ID> done`。
   - **`--design` 形态**：阶段 A 设计（澄清→`design.md`/`plan.md`）→ `kanban move <ID> ready` → 告知用户待实施 → **停，不进阶段 B**（与 `run --design` 一致）。

> 阶段 A 会自行 `kanban move <ID> doing`，无需在 create 后手动 move ready。

### 变体 3：`create --backfill <标题>`（把本会话已在做的工作补录为任务，会话继续推进）

**核心场景**：会话进行到一半才发现忘了从看板任务起步——直接开干了。此时不是"事后归档已完成工作"，而是**为正在进行的会话补一个任务锚点，让后续工作挂在它下面继续**。因此任务落在 **doing**（非 done），补录的是「已做部分 + 识别出的后续待办」，等会话真正做完剩余工作、走正常收尾流程再 move done。

1. `kanban new "<标题>"` → 解析新 ID 与任务目录路径。
2. 读 `main.md`，Edit **首次填充** `## 描述` 段（用输入描述，作为需求背景）。
3. **重建 `## 子任务` 段**：回溯本会话**已完成**的实际工作，拆成带编号子任务并标 `[x]`（`- [x] NN 文本`）；再据描述与会话意图，把**识别出的后续待办**也加进来，标 `[ ]`（`- [ ] NN 文本`）。编号 01/02/03… 全局递增。**已做与未做必须如实区分**。
4. **补已做部分的设计与计划**（从本会话真实改动提炼，诚实回溯）：
   - `design.md`：截至补录时**实际采用**的设计方案（背景/目标/设计决策/接口/边界）。
   - `plan.md`：截至补录时的实施情况——已完成的步骤标 `[x]`、待办的标 `[ ]`，与子任务清单一致。
5. **写 `logs.md`**：一条补录条目（标明「本任务系会话中途补录，已完成部分 …，剩余工作 …」，记本地时间戳、阶段标「doing·补录」）。
6. `kanban move <新ID> doing` —— **落在 doing**，让会话继续在此任务下推进。
7. **询问下一步（必做，落 doing 后立即）**：用 **`AskUserQuestion` 工具**发起**点击式**询问，把当前进度（已完成 X 项、剩余 Y 项）写进问题，提供选项：
   - 「继续做下一项」（推荐，置首）：直接进入 `/kanban run <新ID>` 的实施流程，取首个未勾选 `[ ]` 子任务推进——执行纪律见下方「若选择继续推进」。
   - 「结束任务（move done）」：收尾。**若仍有未勾选 `[ ]` 子任务**，先用纯文本提醒「还有 N 项未完成：…」并追问是否仍要结束；确认后按阶段 C 收尾（补 `notes.md`/`readme.md`、`logs.md` 收尾条）再 `move done`，绝不静默丢弃未完成项。无剩余 `[ ]` 时直接走收尾。
   - 用户选「Other」或给出其他指令：按其输入执行（如 `/kanban update` 补需求、切到别的任务、或直接输入下一条指令）。

**若选择继续推进（执行纪律）**：会话后续工作挂在该任务上——执行剩余 `[ ]` 子任务时按 `/kanban run <新ID>` 的实施纪律推进（先 `kanban show` 读最新状态、逐条完成 → `kanban check`、增量写 `logs.md`）；全部子任务勾完后再走阶段 C 收尾（届时才生成 `notes.md`/`readme.md`）并 `move done`。**`notes.md`/`readme.md` 在收尾（move done）前不要写**——任务未结束。

**backfill 硬性约束：**

- **不做 `AskUserQuestion` 澄清**——已完成部分有会话记录为证；剩余待办若不明确，用 `AskUserQuestion` 与用户对齐**仅限后续范围**，已做部分不问。
- **诚实重建**：`design.md`/子任务/`logs.md` 必须反映本会话**真实做过**的事，绝不把「按设计本应做但没做」的写成「已做」；已做 `[x]` 与未做 `[ ]` 严格区分。
- **文档从会话历史提炼**，而非凭空生成。若已做部分不足以撑起完整 `design.md`，照实写已有的部分、留白缺失部分，不注水。
- **默认落 doing 而非 done**——补录是为承接后续会话，不是收尾；仅当用户在步骤 7 明确选「结束任务」时才走 move done。`notes.md`/`readme.md` 留到真正收尾（move done）前再写。

## 对已有任务补需求并重开（/kanban update）

当任务（含 `done`）事后发现要追加需求，用 `kanban update` 在原任务上下文上叠加一轮工作，**而非新建任务**。

**斜杠命令 → CLI flag 意图映射（agent 解析 `/kanban` 输入时按此判定）**：

| 用户输入形态 | 判定 | 执行的 CLI |
|------|------|-----------|
| `/kanban update <ID> <需求>` （无 flag） | 默认补完就做 | `kanban update <ID> <需求>` |
| `/kanban update --no-run <ID> <需求>` | 显式 opt-out | `kanban update --no-run <ID> <需求>` |
| "给 0010 补个需求：xxx" / "0010 还要 xxx" | 自然语言，默认 | `kanban update 0010 xxx`（默认立即执行） |
| "给 0010 补个需求，但稍后做/先别做/只补需求：xxx" | 自然语言表达"不立即" | `kanban update --no-run 0010 xxx` |

即：**默认补完就做**（无 flag 时 agent 追加后直接接着按 run 流程处理刚追加的编号，不再等 `/kanban run`）；**只有用户明确表达"稍后做/先别做/只补需求"之意（无论显式 `--no-run` 还是自然语言），才加 `--no-run` 只补需求、不执行**。

1. **追加需求并重开**：`kanban update <ID> <需求文本>` —— 往 `## 子任务` 段追加一条 `- [ ] NN [补充] 需求文本`（编号自动递增），并把任务移到 `doing`（`done` 可回流；`archive` 任务需先解除存档）。
   - **默认补了就做**：无 flag 时 `kanban update <ID> <需求文本>` 追加后**立即执行刚追加的这条**（agent 接着按 run 流程处理该编号，完成后 `check` 勾上），省去再单独 `/kanban run` 的步骤，避免忘记。
   - **只补需求、稍后做**：加 `--no-run` —— `kanban update --no-run <ID> <需求文本>`。仅追加并重开到 doing，等用户后续主动 `/kanban run <ID>` 再执行。
2. **按 run 流程执行**：随后 `/kanban run <ID>`。run 读子任务清单，找**第一个未勾选**的子任务——那就是本轮目标。**已勾选（`[x]`）的子任务视为已执行，跳过**。这样多次 update 堆积的补充需求，每次 run 只处理最早未执行的那条，逐条消化、绝不重复执行。
3. **补充需求走增量**：带 `[补充]` 标签的子任务，先读已有 `design.md`/`notes.md`/源码作为基线，只实现新需求；文档用追加"第 N 轮"小节，不重写历史段。
4. **执行后勾上**：`kanban check <ID> <编号>` 把刚完成的子任务标为 `[x]`。
5. **再次完成**：所有子任务都勾上后，`move <ID> done`。

**示例**：0010 已完成（子任务 01/02 都 `[x]`），事后想到"存档也要二次确认"，又想到"删除也要二次确认"：
```
kanban update 0010 存档也要二次确认            # 默认：追加「- [ ] 03 [补充] 存档也要二次确认」+ 重开，立即执行 03，完成后 kanban check 0010 03
kanban update --no-run 0010 删除也要二次确认   # 只补需求：追加「- [ ] 04 [补充] 删除也要二次确认」+ 重开，不执行，留待稍后 run
kanban show 0010                              # 确认 01/02/03 已勾选，04 待执行
/kanban run 0010                              # 稍后主动 run 取首个未勾选=04，实现删除二次确认
```
